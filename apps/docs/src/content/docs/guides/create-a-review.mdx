Keep Whiteboard open and use a [connected agent](/agents/) in your local
repository. The agent can request permission to read files or fetch commits.
Read those requests before approving them.

## Choose what to review

A base revision is the starting point for a comparison. Tell the agent which
changes to include.

### A branch

If your base branch is not `main`, replace it in this prompt:

```text
Review my current branch against up-to-date main and open the result in Whiteboard.
Start with the purpose of the change, then explain the main behavior changes.
Link the explanation to the relevant code and call out open questions.
```

### A pull request

Use a GitHub pull request URL that your account can access:

```text
Review <pull-request-url> in Whiteboard.
Explain the purpose, behavior changes, and open questions. Link each claim to code.
```

If a review already exists for that pull request, Whiteboard can return it. If
the pull request changes, ask the agent to update that review.

### Specific commits

Replace the placeholders with the revisions you want to compare:

```text
Review the changes from <base-commit> to <head-commit> in Whiteboard.
Explain the behavior changes and link them to the affected code.
```

### Uncommitted work

A working-copy review uses files in your local checkout. To review only
uncommitted changes, ask:

```text
Review my uncommitted changes against HEAD in Whiteboard.
Use a working-copy target with base HEAD. Explain the changes and link them to code.
```

To include branch commits and uncommitted work, ask:

```text
Review my current checkout, including uncommitted changes, against the default
branch in Whiteboard. Use a working-copy target.
```

## Read the review

Make sure that the review uses the intended repository and revisions. Start with
the purpose of the change. Compare the behavior before and after the change. The
agent chooses the sections and diagrams, so each review can differ.

Whiteboard fills in the review while the agent writes it. You can read completed
sections before the agent finishes.

Select a diagram step or a code reference to open its source. If an element has
no source link, ask the agent to add one.

If a link opens the wrong code, make sure that the review uses the intended
repository and revisions. Ask the agent to correct the comparison and links.

### Inspect the diff

Open the Diff view to compare the code versions. Structural diffs compare code
syntax rather than lines alone. Folds hide sections of code until you expand
them.

<DemoFigure
  image={diffSummary}
  alt="A diff with folded imports and unchanged lines, plus a function summarized as pseudocode"
  caption="The dev.fast demo shows folded lines and a function summary. Expand a folded section to read its code."
/>

Collapsed tests, documentation, or function bodies are not necessarily absent
from the change. Expand them to read the code. Open Settings → Experimental
Features → Structural Diffs → Diff display and AI summaries to change folding
and file hiding. Reload the window when prompted.

### Enable pseudocode summaries

Pseudocode describes code with short, readable steps. In v0.2.0, diffr uses
Gemini to summarize large new functions and tests. This requires a Gemini API
key, separate from your coding agent's model access.

Do not enable summaries for code that you cannot send to Gemini. The summarizer
sends source-file contents to Gemini.

To enable summaries:

1. Open Settings → Experimental Features.
2. Enable Structural Diffs if it is off.
3. Open Diff display and AI summaries.
4. Enable summaries and enter a Gemini API key and model.
5. Select Save summaries.
6. Reload the window when prompted.

Test setup sends synthetic code without saving the configuration. Read the
original source before relying on a summary.

If summaries do not appear, use Test setup to test the Gemini API key and model.
Save the configuration and reload the window when prompted. Summaries apply to
large new functions and tests, not every change.

## Ask questions and request changes

Use Copy for Agent to send a selection back to your existing agent conversation.
Add a request for the information that is missing. For example:

```text
Show the proposed API, examples, and motivation before the implementation details.
Link the explanation to the code.
```

Whiteboard does not directly edit source files. Give code-change requests to
your coding agent. Then ask it to update the comparison and explanation.

Ask Agent can answer questions about selected text inside Whiteboard. It is a
preview feature with agent-specific permissions. See
[Ask and give feedback](/guides/give-feedback/) for both workflows.

## Update the review

Commit comparisons use pinned revisions, which are fixed versions of the code.
Later commits do not appear until the agent updates the comparison.

Working-copy source and diffs refresh as local files change. The written
explanation does not update itself. Ask the agent to revise it after changing
the code.

```text
Update this Whiteboard review to include my latest changes.
Update the comparison, explanation, and code links. Remove claims that no longer apply.
```

## Understand agent decisions

The Decision Log links review quotes to the agent conversations behind them. It
needs access to that history. Without it, ask the agent to state what it can
support from the code and what remains unknown.

Trace capture records agent conversations. It is experimental and requires
storage configuration. Open Settings → Experimental Features → Trace capture.
The configuration supports your own S3/R2 bucket or the hosted trace store.

Read [Privacy and data](/help/privacy/#hosted-trace-store) before enabling trace
capture. Capture uploads agent transcripts to the selected store. For the hosted
store, authorize only repositories whose transcripts you can upload. Turning on
capture does not recreate missing past conversations.

## Share the result

Select Share review to upload a snapshot, a fixed copy of the review. If you are
already signed in, the upload starts immediately. Read the review before
selecting Share review. Its text and images can contain code or private project
details.

Anyone with the link can download the snapshot. Readers need their own
repository access to open the code. Later edits do not change the shared copy.

See [Share a review](/guides/share-a-review/) for sign-in steps, updated
snapshots, and link revocation.

## Optional configuration

Open Settings to change how you read reviews:

- Select Editor → Document width → Wide or Full for more room for diagrams and
  code.
- Select Notifications → Review ready to enable completion notifications for
  reviews you are not viewing.
- Select Editor → Keymap for Vim, Emacs, or Sublime Text keys. Reload the window
  after the change.

Review-ready notifications are off by default.

### Explain code without a review

Scratchpad is an experimental page for visual explanations, not a change review.
It can include code from more than one repository. Enable it under Settings →
Experimental Features → Scratchpad. Then ask your connected agent:

```text
Explain how this request reaches the database on the Whiteboard scratchpad.
Draw the call path and link each step to code.
```

New entries appear at the top. The scratchpad cannot be shared as a review.
